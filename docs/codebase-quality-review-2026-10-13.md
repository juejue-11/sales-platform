## Standards

此轴线列出设计启发式与工程流程缺口，未发现必须按外部风格指南判定的硬性违规。优先级：P1 为会影响日常业务正确性的缺陷；P2 为应计划治理的维护/交付风险；P3 为局部优化。

### Python 审查：5 项

1. **P2：应用中心类仍然承担多种职责。** `backend/application/service.py:72` 的 `ScreeningService` 管理生命周期、配置、导入、附件刷新、项目查询、分析调度、研究历史、人工决策和状态。`run_job` 在同一流程串联快照、数据库、进程协议、研究工具、引用校验与过期重排；`backend/main.py:164` 还直接使用私有 `_ai_config()`。这是可能的 Divergent Change，建议按事务与运行契约逐步提取任务执行和配置职责。
2. **P2：调查模块的网络、存储和政策集中。** `backend/research/project_research.py:738` 的 `ResearchSession` 同时处理请求/重定向预算、来源与版本存储、搜索适配、文档解析、证据关系和工具分发。不同类型的变化会集中触碰同一实现，应分别确定可验证的内部 seam。
3. **P2：AI 协议与业务验证混合。** `backend/analysis/ai.py:311` 起的 provider 桥接处理子进程、流式协议、回调和预算；`validate_judgment` 处理报告与来源证据以及企业能力政策。进程通信变化和业务判断变化共享回归面，需后续独立批次拆分。
4. **P2：Python 依赖和规范门禁不可复现。** 筛选 `requirements.txt:1` 使用开放下限；采集 `requirements.txt:1` 虽有部分上限，仍无精确锁定或 hashes。仓库内未见统一 ruff/格式化/Python 类型检查配置或 CI。安装脚本每次解析版本范围，测试环境与新安装环境可能不同。
5. **P3：采集重试策略重复。** `collector/fetch.py:27` 的 GET 与 `:51` 的 POST 重复限速、重试与退避分支。将来修改策略需要同步两处，宜在采集模块内部收拢真实共享行为。

### Frontend / Agent 审查：4 项

1. **P3：研究展示模块自取数据是需要说明的设计取舍。** `frontend/src/components/research/ResearchDisplay.tsx:120`、`:322` 内部管理快照和历史请求。项目约定没有明确禁止这种封装，不能判为硬违规；必要时可在研究模块内部提取请求 hook，同时保留小的外部接口，不应机械地把所有请求搬进页面。
2. **P2：状态轮询存在旧响应覆盖风险。** `frontend/src/pages/Operations.tsx:62` 无序号或取消机制，`:75` 每 10 秒发起新请求。请求较慢或同时手动刷新时可能重叠，早发后到的响应可覆盖较新状态；本轮为静态风险判断，未做浏览器竞态复现。
3. **P2：HTTP 返回类型主要靠断言。** `frontend/src/api.ts:38` 的请求函数最终 `as T`，编译期 strict 不能验证实际 JSON。建议针对高风险接口增加窄解析或接口契约测试，并明确协议版本；这不意味着已观察到错误响应。
4. **P2：测试命令与构建门禁未形成统一链路。** 前端 `package.json:6` 没有 test/lint 入口，浏览器 QA 依赖手动运行；Agent `package.json:10` 的 test 只运行 dist。当前产物已证明与源码一致，但未来直接运行 test 仍可能测试旧产物，应在门禁中先构建。

### 版本与交付治理：1 项

1. **P2：两个系统缺少一致的源码版本管理。** 正式采集目录未受 Git 管理；筛选最近两轮改动仍在未提交工作区。已有源码快照、逐文件哈希与恢复验证，能帮助本次恢复，但不能替代持续的变更历史、评审记录和版本化发布。建议把采集源码纳入版本控制，并把已验收批次整理成可审阅的提交；不要把数据库、密钥和运行归档纳入源码仓库。

Standards 共 10 项改进建议/流程缺口；没有将外部指南未采纳的风格认定为仓库硬违规。主要风险是核心职责集中与缺少自动、可重复的质量门禁。

## Spec

### 已在临时数据中复现的 2 项缺陷

1. **P1：保存的导入路径重启后未恢复。** README 的数据与更新说明允许在配置页更改导入路径；设置接口定义见 `API_CONTRACT.md:163`。`service.py:382` 更新当前对象的路径并保存配置，但构造器 `:88` 重建时仍使用环境/默认路径，没有回读保存值。复现时无导入路径环境变量，默认路径 A 与配置路径 B 均为临时文件：保存 B、关闭、重新打开同一临时数据库，配置仍显示 B，实际 `source_path` 却是 A。这会导致重启后读取/监控错误文件。
2. **P2：异常退出后的旧 Agent 运行记录未收尾。** README 说明重新启动恢复后台运行，`API_CONTRACT.md:91` 定义 Agent 运行状态。`service.py:204` 将运行中 job 改回 queued，`:1462` 仅按具体运行 ID 在正常结束路径收尾。模拟临时数据库中的崩溃状态后执行启动恢复，job 已排队，旧 AgentRun 仍是 running、结束时间为空；创建新的运行记录也不会结束旧记录。历史与任务状态可能长期不一致。

两项复现仅使用临时数据库和临时文件，未调用模型、真实来源或正式 HTTP 接口，没有启动后台任务，也没有修改正式设置。复现工具位于工作区 `tmp/backend-layout-20261013/reproduce_audit_findings.py`。

### 运行建议与验收边界

1. **P2，可观测性建议：** `backend/main.py:78` 的 health 固定返回成功，符合当前契约；`service.py:220` 的 worker 异常仅休眠。导入循环会保存错误，但 worker 缺少统一日志、心跳与最后进度。不能由健康成功证明业务队列健康，也不能据此断言现有队列已失效。

3. **P2，解释器一致性建议：** `register_daily_task.ps1:5` 使用注册时 PATH 中的 Python，再写入解释器路径；未核验它与安装依赖的环境一致。从其他环境注册后可能导致定时采集缺依赖，尚未观察到本机实际失败。

## 建议推进方式

运行契约线：补两项重启回归并修复路径恢复、旧 AgentRun 收尾，再补队列诊断。工程规范线：明确 Python/TS 风格及类型规则，建立一个可重复的检查入口和 CI；锁定 Python 依赖，完善两个系统的版本管理。结构线：在这些基线下，逐步深化任务执行、调查和 AI 协议职责，不再仅按文件长度拆分。

每一批次在隔离环境验收，发布与重启另行处理。大厂原则应转成适合本项目的可执行门禁，不能只把代码搬进更多目录，或以一次测试通过代替持续工程质量。
