# 采购事实与原始资料

项目详情的采购信息先展示结构化事实，再提供证据和原始资料。公告正文和附件是并列的来源，不能用“已解析”替代事实正确性的判断。

## 数据边界

- 采集系统保存原始正文、文件、版本和归档；筛选系统不写入采集数据。
- `backend/procurement/` 使用现有正文规则、附件解析结果和摘要规则归纳采购事实，保留冲突和缺口。
- 前端负责分组、筛选、字段呈现和证据阅读；不调用研判 Agent 生成页面字段。
- 研判 Agent 可以请求读取公开附件，并使用已读取证据生成分析、潜在线索和行动建议。

## 接口兼容

复用 `GET /api/projects/{project_id}` 和 `POST /api/projects/{project_id}/documents/refresh`。保留原 `procurement.items`、交付字段、附件状态和 `briefing`；采购聚合新增可选 `facts`，物料行新增可选 `sources`、`status`。

事实字段包括 `scope`、`delivery_period`、`delivery_location`、`qualification` 和 `contact`。每项事实包含 `id`、`field`、`value`、`status`、可选 `note` 和 `sources`。状态为 `extracted`、`uncertain` 或 `conflict`；`extracted` 仅表示规则已提取，不表示人工核实。

来源包含 `source_kind`、`record_id`、原文 `quote`，附件来源另外包含 `document_id`、可选实际 `page` 和版本 `sha256`。没有实际分页的资料不编造页码；缺少摘录或来源无法匹配时明确提示，不能把字段拼接成原文证据。

同一需求合并时保留多个来源，技术规格不同的物料继续分开展示。互相冲突的数量或交付说法保留双方值和来源，避免静默覆盖或作为累计数量展示。资格条件可能相互补充，不能仅因文字不同就判断为冲突。

附件阅读复用 `GET /api/projects/{project_id}/documents/{document_id}/snapshot?sha256=...`，按项目及版本约束访问保存快照。公告正文来自已返回的 `records`，归档下载继续使用 `GET /api/records/{record_id}/archive`，返回原始文件。

## 阅读与追溯

采购页中的正文只显示固定行数预览。完整正文、关键词匹配及来源定位在独立抽屉内进行。阅读文本仅清理采集节点产生的碎片换行，保留段落和原始文本查看入口，不改变后端正文、原始证据摘录或归档文件。

来源定位在对应记录或附件页内查找摘录，允许忽略采集产生的空白差异。未找到摘录时显示未定位状态，不将第一行冒充匹配位置。前后端的加载失败、受限文件及空资料状态均应可辨识。

## 验证

后端回归覆盖来源合并、规格差异、标量冲突、缺失摘录及原始文件保留；HTTP 回归覆盖详情、资料刷新、版本快照和归档下载。浏览器验收覆盖正文预览、抽屉搜索与定位、附件失败、冲突数量、旧接口兼容、其他详情标签页及移动端布局。
